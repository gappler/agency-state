The practice

From brand book to working system

A brand book can guide a person, but AI needs a system.

One rule, end to end

A brand book might say the brand never uses hype: no "ultimate," no "game-changing," no exclamation points. The rule is clear on paper, but no one can tell whether a machine followed it until it becomes something the checks can catch.

So the failure looks like this:

Conquer the backcountry with our ultimate, game-changing pack!

The same rule, made checkable:

never_say: - ultimate - game-changing formatting: - no-exclamation

Run the draft through the rule check and it reports back in plain English:

[block] ultimate is on the never-say list [block] game-changing is on the never-say list [block] exclamation points are not allowed

A sentence in the brand book becomes a rule the system can check against the work.

Step 1: Assess readiness

The work starts with the existing documents: the brand book, the site, the design system, and the campaigns, plus the people who own the brand. The assessment sorts all of that into what a machine can take as settled and what still needs a person: which rules are current and sourced, which visual decisions live in examples and should become stated rules, which approvals belong to someone and should say so.

That sorting is the readiness call. If the brand itself is still being decided, brand strategy comes first.

Step 2: Codify the source

When there is enough to work from, the brand becomes source a machine can read and the team can govern.

Agency State's BrandBuilder reads the team's documents and produces the codified brand in two forms. The team reviews and revises the source files; the system runs on the compiled contracts:

.brand/ source/ brand.yaml voice.yaml visual.yaml positioning.yaml architecture.yaml rules.yaml products.yaml narrative.md needs-review.yaml brand-runtime.json interaction-policy.json tokens.json

The source files hold the structured extraction: voice, visual identity, positioning, rules, product facts. The needs-review file lists the inferences codification made, the conflicts it found, and the decisions left for a person. The compiled contracts come after that review: the brand runtime is the fast version the machine reads before it writes, the interaction policy is the subset of rules the checks use, and design tokens carry exact values for color and type.

The file format matters less than the discipline underneath it. If a value came from the brand book, the source should say where. If a rule was inferred, it should be labeled as inferred. If the source is silent, the question goes to a person instead of the machine quietly inventing an answer and calling it the brand.

Extraction pulls structure from what already exists; judgment decides what the brand means when the source is stale or in conflict.

BrandBuilder checks that discipline by asking whether the source labels are accurate: if a rule says it came verbatim from the brand book, did that language actually appear there? If a citation points to a section, does that section exist?

rule: "No exclamation points." source: "brand-book, Boundaries" basis: verbatim

An invented source label goes back to a person before the rule enters the system.

Step 3: Serve, check, route

Once the source is reviewed and compiled, the brand starts showing up in the work, and the system begins to feel like infrastructure.

Before a draft starts, the system serves the machine the parts of the brand the task needs: the voice guidance, the product facts, and the interaction policy. Every model and tool the team uses reads from the same source.

Giving the model the right source helps, often a lot, but it does not prove the output matches the source. So after the work exists, the checks run on what the brand has already settled, and everything that needs judgment routes to the person who owns the decision.

Step 4: Close the loop

By the time work reaches review, the checks have caught the banned words, the off-palette colors, and the wrong fonts. Attention only goes where it is needed.

A fix the reviewer keeps making turns into a rule the check catches from then on, and a fact the copy keeps getting wrong is fixed once, in the source the machine reads. That loop keeps the system current as the brand, the products, and the team's tolerance change. That is a Brand OS, and it runs on an operating habit: update the source, recompile, improve the checks, so the team works from the same place.

The result

Run the four steps and the brand book becomes a working system: source the team governs, compiled contracts the machine reads, checks on the settled decisions, routes that put a person where judgment is needed, and a loop that keeps all of it current. The Brand OS build map lays out that system.
