The practice

Serving the brand with MCP

A brand MCP is a serving layer for a codified brand: the source lives in one place, served to AI tools while the work is happening.

MCP is usually discussed in relation to repositories, databases, tickets, docs, and tools. Brand belongs in that conversation. A brand team has source material, product facts, approved language, visual constraints, and review logic. That is operating material.

The useful question is what the brand needs to answer while the work is happening.

Which voice rules apply to this channel? What source supports this product fact? Can this claim be used without a condition? Which phrases are banned, discouraged, or approved? What visual rules apply to this surface? What needs human review?

The server does not create those answers by itself. The brand has to be shaped first. The source needs to be structured, reviewed, and maintained so the server can return something useful when a tool asks.

Source and server

The Agency State example has two parts.

The source lives in agency-state-brand. That repo holds the brand platform and visual guidelines. It is the canonical place for the approved brand, not a draft space and not an application.

The server lives in agency-state-brand-mcp. It reads from the source and exposes the brand through tools such as:

get_identity get_positioning get_audience get_brand_voice get_vocabulary get_never_say get_proof get_boundaries get_competencies get_full_platform get_visual_identity

That split matters. The brand source can stay clean, governed, and readable by humans. The MCP server can handle the serving behavior: what tools exist, what each tool returns, how the content is cached, and how clients connect to it.

In this example, the server is deployed on Railway because MCP clients need a reachable endpoint. Railway gives the server a public /mcp URL without turning the brand source itself into an app. When the brand source changes, the server can pick up the new content from the repo without a redeploy. When the server behavior changes, the MCP repo changes and Railway redeploys it.

What the server looks like

For Agency State, Claude Code built a small Python server with FastMCP. The shape is simple:

source: agency-state-brand server: agency-state-brand-mcp host: Railway clients: Claude Code, n8n

The server knows where the source lives, reads the current brand files, keeps a short cache, and registers each useful section as a tool. In plain terms:

1. Fetch brand-platform.md and brand-guidelines.md. 2. Use a bundled fallback if the fetch fails. 3. Slice the brand platform by section. 4. Return one useful section when a tool asks for it. 5. Run at a reachable /mcp endpoint.

That is enough to prove the pattern. The technical build matters, but the larger design decision is the tool list. A brand server becomes useful when it exposes the questions the work actually asks.

How a tool uses it

A tool asks for the slice of the brand that applies to the work in front of it.

For Agency State, a writing workflow can ask for voice guidance and never-say language before drafting. A page build can ask for the visual identity. A review workflow can ask for boundaries, proof, or vocabulary before checking the work.

In a more developed codified brand, the tools move from document sections to work patterns:

get_voice(channel: "paid search") get_claim_rules(topic: "ice retention") get_product_facts(product: "Yowie 35QT") get_review_criteria(format: "landing page") get_visual_rules(surface: "web page")

That is the design work: deciding which brand decisions the work needs access to, and how the server should expose them.

Implementation path

A practical brand MCP starts before the server.

First, gather the source material: brand books, websites, product facts, voice guidance, and review patterns.

Then extract the brand into structured files a team can read, correct, approve, and improve. In the Agency State example, the server serves the hand-maintained brand platform and guidelines directly, which is enough to show the serving pattern. For client work, the stronger pattern is fuller codification before serving. Agency State's BrandBuilder fits there: it turns decided brand material into reviewable source files before they become the source the system uses. The source needs provenance where facts and claims are involved, and ownership where judgment is involved.

After that, design the server around the work. Some tools may return whole sections. Others may answer narrower questions. The right shape depends on where the brand is being used: drafting, review, campaign planning, or workflow automation.

Then connect the server to the tools doing the work. For Agency State, Railway hosts the reachable /mcp endpoint. Claude Code can call the brand tools, and an n8n workflow consumes the same server. For a client, the same pattern could run locally, in a team environment, or behind a managed endpoint. The hosting choice follows the privacy, permissions, and partner access requirements.

The maintenance model is part of the implementation. Someone has to own source updates, approve changes, manage access, and decide when the server's answers need to change.

Why it matters

Without a serving layer, brand context tends to scatter. One copy lives in a prompt. Another lives in a custom assistant. Another gets uploaded to a tool. Another sits in an agency deck. Each copy can drift.

Every tool, workflow, and check reads from the same brand source instead of keeping its own copy. That matters for drafting, but it matters even more for review: the same source that helps a model write can also help the system check what the model made.

A brand MCP is buildable. The hard part is shaping the source and giving the tools doing the work a stable connection to it.
